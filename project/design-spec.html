Classroom Data

A teacher-facing reporting dashboard that surfaces STEM and ELA learning activity across a class, plus a student-level drill-in page. Teachers see engagement metrics, reading levels, quiz performance, and content breakdowns — all filterable by school, activity type, and date range. Clicking a student name navigates to an individual student view.

Status: Design WIP Source: index.html Student page: stem-reporting-8z9b.vercel.app ↗ Design system: Angelou Design System 2.0

Overview §

A live preview of the classroom prototype alongside the four core design principles guiding this feature. The student-level page is a separate Next.js app deployed to Vercel.

Design Principles
Data first, chrome second
Metrics and tables are the content. Navigation and chrome exist only to support access to data, never to compete with it.
One tab, one context
STEM and ELA are distinct pedagogical contexts. Never blend their metrics or share cards between tabs.
8px grid, always
All spacing and sizing is a multiple of 8px (with 4px as the only exception for hairline icon–label gaps).
Motion communicates data
Entrance animations on charts draw attention to the data loading — they are not decorative. Every animation has a functional intent.

Pattern: Entrance Animations §

All data-driven elements animate into view on mount. The pattern is consistent: delay 80ms → trigger visibility → CSS transition runs.

Anatomy

  1. Component mounts with visible = false state
  2. useEffect fires a 80ms setTimeout, then sets visible = true
  3. Elements render with width: 0% (bars) or stroke-dasharray: 0 C (arcs)
  4. When visible flips, CSS transition animates to the real value
  5. Each element in a list gets transitionDelay: i × 80ms stagger
Do

Reuse this exact pattern for any new data-visualization element. The 80ms initial delay + stagger is the established convention in this codebase.

Don't

Don't use CSS @keyframes for data bars — the JS state pattern is necessary so the animation runs after React has committed the real values to the DOM.

Do

Always set explicit width and height attributes or inline styles on SVG icons. Never rely on CSS classes that may be overridden.

Don't

Don't mix stroke and fill icon styles within the same card or component. Pick one family per visual context.

How to Extend §

Six principles for designing adjacent screens or new metrics within this product area.

  1. Start from CSS variables, not raw values. Every color, spacing, and radius in this spec has a CSS variable. New components should reference those variables — never hardcode a hex value in component code.
  2. Respect the STEM / ELA boundary. These are different pedagogical contexts. A "student activity" card can serve both with different items props — but skill-specific metrics (Lexile, reading level, writing) are ELA only. Disciplines are STEM only.
  3. Data visualizations must animate. Every new chart or metric that represents quantity should use the visibility-state pattern (80ms delay, staggered transitions). Static data presentation is the exception, not the rule.
  4. Add new filter dimensions via REPORT_DATA, not new components. The Filters component and Dropdown already support any option array. Adding a new filter is a data change, not a component change.
  5. Status badge is config-driven. Classroom prototype: edit window.__STATUS in index.html. Student page: edit constants at top of StatusBadge.tsx. No component code changes needed. When the project hits "Design ready", add the handoffUrl pointing to this file.
  6. Bump ?v=N on every file change. All scripts and styles are cache-busted via query params in index.html. Forgetting to increment the version is the #1 cause of changes not appearing in Vercel deploys.
